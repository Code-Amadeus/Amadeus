## 结果与取舍

同一产品代码、60 FPS 最近邻采样、384 MiB FrameStore、GPU GC 60/30、同一全素材路线，
各运行 600 秒。两份独立缓存均为 7451 文件、2610366484 字节，逐文件哈希一致；两组首次转码均为 0。
CPU 是全程累计 CPU 时间折算的单核百分比，内存是剔除前 20 秒后的原生计数均值。

| 指标 | 静态帧对照 | 全量视频 | 变化 |
| --- | ---: | ---: | ---: |
| CPU，单核等效 | 80.99% | 47.71% | −41.1% |
| 全进程私有工作集 | 833.78 MiB | 792.89 MiB | −40.89 MiB（−4.9%） |
| 私有提交量 | 1228.12 MiB | 1209.58 MiB | −18.54 MiB |
| 进程独立 GPU 内存 | 247.52 MiB | 247.51 MiB | 基本持平 |
| 进程共享 GPU 内存 | 52.36 MiB | 92.17 MiB | +39.81 MiB |

本轮主要收益是 CPU，超过维护者提出的 25% 门槛。不能称为 RAM／VRAM 再降一个数量级，
也不能把私有工作集与共享 GPU 内存直接相加。两组 FrameStore 平均仍接近 384 MiB 上限；
视频还承担有界解码表面和 RGBA 输出的费用。因此保留平衡候选，不继续为了小幅内存收益扫预算。
上述表格包含相同离屏回读负担，只用于该配对比较；不冒充真实桌面宿主的绝对占用。

## 本轮修复

1. 将常驻保护与加载优先级分开。未播放片段的海报不再抢占当前播放；当前闭嘴帧和嘴型仍明确获得当前优先级。
2. 单片段试验入口扩展为多片段注册表：只有当前源拥有解码器，旧输出仅保留到替换画面到达。
   异步加载可撤销，旧回调不能污染新片段，失败按片段锁存。压缩视频按需加载，不把整包常驻 RAM。
3. 嘴型继续使用当前显示的 sourceIndex、anchorTrack、openness 和精确静态闭嘴帧；未另造一套嘴型时间轴。
4. 推测性入口预取只服从自身头部时长；当前窗口补齐解码启动头。视频终帧只为当前片段额外常驻。
5. 精确静态 hold 的需求不再扩散到推测性预取；新增测试先失败，再修复通过。
6. 依据实际帧 URL 序列与间隔识别 happy → smile 别名，共享已核验视频描述，不猜测 tag 拼写。
   正式素材为 39 组，运行时素材路线覆盖 40 个标签（含该别名）。原始行为图的 37 个节点会由运行时补入 smile/sad，
   首次路线退出的实际原因是无图节点的 happy；旧失败记录保持原样。

### 呈现停顿的归因边界

旧离屏回读方式的 600 秒配对各有 4 个孤立入口 miss；静态和视频都在首轮出现约
638／829 ms 的呈现间隔。它们没有对应 >50 ms 的被监测 GL／decoder 调用或 JS 长任务，
也不能据此归因于解码器、GPU GC 或 HTTP 服务器。

正式产品的普通 BrowserWindow 不消费探针的连续 NativeImage 回读。增加显式共享 GPU 输出对照，
每次 paint 立即 release texture 后，全素材及公开 tag 两轮都未复现 >50 ms 间隔，
两轮最大 ticker 间隔分别为 44.6／31.3 ms。这支持离屏回读干扰解释，后续流畅度实验使用该输出方式，
同时保留原方式以重现历史测量。没有把不同输出方式的 CPU／内存结果混算。

此前旧版本一次持续约 1.067 秒的“ticker 正常但供帧停滞”原始失败仍保留：本轮没有复现，
但旧日志缺少请求级时序，不能声称已证明它与这次呈现间隔具有相同根因，也不能倒改旧失败为通过。
真实桌面集成验证仍应包含该长循环与实时语音打断场景。

最终回归：**177 项 Node、30 项 Python、语音结束交接检查全部通过**。最终资源配对使用
Electron 44.0.0／Chromium 152.0.7977.54；视频与静态使用相同产品代码，运行过程中源码未改变。

## 冻结与复用

保持 384 MiB、60 FPS 采样、50 ms 第一跳入口、当前 500 ms 窗口、GPU GC 60/30。
