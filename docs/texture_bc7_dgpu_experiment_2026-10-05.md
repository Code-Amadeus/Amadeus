# 8 GiB dGPU：2 GiB 纹理预算、采样与 BC7 磁盘缓存

本轮支持继续推进 **2 GiB 预算 + 60 FPS 采样 + 本地 BC7 缓存**。缓存命中后，renderer 后 5 分钟 CPU 比当前版下降 67.3%，所测进程合计 CPU 下降 39.6%，renderer 私有内存峰值基本相同。不过实际显存占用上升，闭眼片段也仍有一次连续缺帧窗口；不能宣称全面验收通过或已经解决闭眼加载问题。

本轮是独立实验。日常工作区仍是 `codex/local-pr155-2g` / `00670cb`，默认采样关闭。没有修改日常配置、角色包、依赖或公开 PR，也没有使用目录联接或删除/归档 worktree。

## 方法和口径

- 实验代码提交 `8d27d39`，生产渲染代码与 PR #155 已发布的 `00670cb` 一致；增量全部在探针、测试和缓存实验目录中。
- RTX 4070 Laptop，8188 MiB，驱动 581.57，ANGLE / D3D11。每组实际 WebGL renderer 都验证为该 GPU，显示纹理格式均为 BC7 (`36492`)。
- `standard`，60 FPS，实际 DPR / renderer resolution 均为 1；2 GiB 仍计入保留的 CPU 副本及潜在 GPU 副本，没有实施上传后释放 CPU 数据。
- 每组 600 秒，分别为当前版、只开启采样、采样加预生成缓存；独立 Electron profile 和 Python 资源宿主，串行运行，各一轮。
- 92 秒的固定片段路线重复执行，包含快转场、说话、蝴蝶、闭眼长循环和 idle2。探针只接管图的片段选择；源动画时钟、采样规则、预取需求、预算、淘汰、上传与嘴型仍使用现有实现。三组计划路线、源码哈希一致，实际动作最大迟到为 62 / 63 / 64 ms。
- 这是可重复的强制切换压力路线，不代表自然图选择的所有路径。每组仅一次，没有测量方差；不把上一台 eGPU 或旧 30 FPS 随机路线的绝对数值混入对照。
- 本轮开始时应用及 ASR/TTS 进程已退出。只测渲染资源路径，不能据此确认用户观察到的约 4 GB 模型与纹理总占用，也没有测语音推理竞争或真实麦克风。
- 每 2 秒记录各进程 CPU 累计时间和内存；独立 `nvidia-smi` 观察整块显卡。GPU 进程私有内存属于系统进程内存，**不是显存**。设备显存数包含其他应用，起始空闲占用约 0.2 GiB。
- 缓存已生成，校验全部原文件哈希发生在播放计时之前。没有清空 Windows 文件缓存；这不是冷磁盘启动基准。

“单核占比”是该进程所有线程 CPU 时间除以墙钟时间，不代表一个固定核心持续被独占，也不是任务管理器的整机 CPU 百分比。所测进程合计包含 renderer、GPU、其他 Electron 进程及 Python 资源宿主；不包含系统中所有进程。

采样组全程 GPU CPU 计数有两个缺失区间，覆盖约 596.075 秒，因此不把其全程各组 CPU 直接相加后称作完整总量。三组后 300 秒的所有进程区间均完整，可用于上表合计比较。

缓存组仍发生 18,169 次重取，与仅采样的 18,173 次几乎一样。它降低的是每次加载成本，没有把纹理全部常驻。平均每次 WASM 解压约 1.02 ms，校验及其等待约 0.69 ms；这不是完整加载耗时或纯 CPU 时间。网络/文件传递、资源对象、上传和绘制开销仍在。

显存均值从 1.15 上升至 1.67 GiB，峰值从 1.76 上升至 1.95 GiB。保留同一个预算不保证驱动实际占用相同；本轮未隔离驱动分配池、GPU 回收与纹理复用各自的贡献，不能把这个差异全部归因于其中一个机制。收益是显著降低 CPU 并维持低 renderer 内存，**不是显存继续下降**。

## 闭眼片段仍未完全通过

三组都在第 4 次 `idle_closed_eye`（`route-3-idle_closed_eye`，计划 327.6 秒进入）出现缺帧：当前版 64 次、采样 46 次、缓存 37 次。

缓存组的 37 次集中在逻辑帧 141–177，连续窗口约 0.62 秒；它不是只缺入口第 0 帧。缓存组其他缺帧为启动 idle 15 次、首次 thinking_trans 1 次。缓存 miss、校验失败、回退及 UASTC 转码均为 0。因此磁盘缓存不是这段残留缺帧的完整修复，具体的需求优先级、预取窗口或容量冲突尚未做专项归因。

下一步优先提取这个已观察到的状态，做针对性的短程重现与调度检查，而不是再扩大预算或重复三组长测。本轮没有顺手修改该问题，避免失去对照的一致性。

## 缓存成本和实现边界

- 使用当前包 `2026.08.29-mouth1` 的 7,552 张身体帧和 16 张嘴型叠层，共 7,568 张。原文件 2,668,156,721 字节；BC7 + zstd-15 负载 2,630,156,701 字节，约 2.45 GiB，比原文件小 1.42%，另有约数 MiB 索引。
- 两个构建 worker 用时 258.77 秒，进程 CPU 457.38 秒。累计转码计时 63.43 秒、压缩计时 352.73 秒；这些 worker 的区间可重叠，不应再与墙钟时间相加。
- 基于仓库相同的 Basis JS/WASM、BC7 格式和转码参数派生数据；逐文件验证无损压缩回环，读取时验证压缩数据及 BC7 字节 SHA-256。相对现有 UASTC→BC7 结果没有额外有损编码，不意味着相对原画无损。
- 写入采用临时文件、flush/fsync、rename，索引最后发布。构建拒绝复用既有目录。播放器的实验读路径由两个 WASM 解压 worker 服务；实际 WebGL 不支持 BPTC 或派生文件无效时回退原 UASTC。
- 这是手动预构建缓存的实验读路径，尚没有日常自动生成、后台排队、损坏文件重建、磁盘容量管理和正式配置入口。缓存的 Windows 文件页也可能占用可回收系统缓存；上表 renderer 私有内存不包含整个系统文件缓存。
- 适配器将解压后的字节交给既有 backend，所以 backend 的旧 `transcodesCompleted` 计数实际包含两种解码任务，`fetchedPayloadBytes` 在缓存组也不是线上压缩传输字节。应使用公共 `render.transcodes` 和 `render.bc7Cache` 区分真实转码、命中及压缩字节。
- 解压器为固定 `zstddec 0.2.0`，下载包 SHA-512 已核对，来源、文件哈希和许可随实验提交保存。没有更改生产依赖清单。

## 验证与证据

最终 85 项聚焦 Node 检查、26 项 Python 汇总检查通过。每组均完整记录 600 秒，0 丢失事件、0 运行中源码变更。伴随模式抑制/恢复、主动 GPU 纹理销毁后重新上传、WebGL 上下文恢复后的像素校验全部通过；最终三组 GL 错误均为 0。

失败记录也保留：首次缓存短测发现非 4 倍数尺寸的 mip level 没有沿用 Basis 的块对齐，导致 GL 错误。修正在实验缓存适配器，新增非对齐尺寸契约测试；修正后的 60 秒短测和 600 秒正式测量均通过。之前固定路线探针的函数返回值导致 Electron 序列化失败，也已修为不跨进程返回函数。
