# 社区插件开发预览与首版插件商店实施计划

日期：2026-10-21

状态：已批准并开始实验施工；第一批 D0/D1 见[施工记录](verification/extensions/community-preview-batch1-2026-10-21.md)，D2/S0 的实现与本地验收见[第二批施工记录](verification/extensions/community-preview-batch2-2026-10-21.md)。S1 下载、安装与耐久安全准入的实现和本地验收见[第三批施工记录](verification/extensions/community-preview-batch3-2026-10-21.md)。S2 浏览、详情、安装进度和手动更新的实现及本地验收见[第四批施工记录](verification/extensions/community-preview-batch4-2026-10-21.md)。S3 的本地打包、真实 shell 和固定 reader 准备见[第五批施工记录](verification/extensions/community-preview-batch5-2026-10-21.md)，公开门槛见[发布检查表](verification/extensions/store-v1.md)。D0 跨仓公开入口、D3 外部作者和 S3 发布资格仍待完成；未合并、未发布。

目标是让外部作者独立完成插件，让用户从精选目录发现、安装和更新插件。先完成 **D0 文档收口 → D1 作者校验入口**，再并行推进 **D2 合约与模板 → D3 外部作者验收** 和 **S0 目录规则 → S1 下载与安装 → S2 商店界面**，在 S3 汇合验收。商店开发使用参考包和测试 fixture，不等待作者招募或公开发布。复用已有安装事务、配置存储、运行时和原生能力接口。

本计划只覆盖已经开放的 TTS、MCP、Skill 和数据主题。首版商店采用维护者审核的公开索引，安装包由作者发布，更新由用户触发。它不承诺稳定 SDK 1.0、任意第三方代码沙箱、自动更新或完整更新回滚。

首版实现还须满足第 16 节的扩展约束：目录收录政策与运行契约分开，新能力由明确的原生 owner 消费，旧客户端能隔离不支持的条目而继续使用兼容目录。这些约束通过现有阶段和合成未来条目验收，不提前开放新的插件类型。

1. 作者文档分散，协议仓首页仍有已过时的“未合并实验”描述；当前支持范围、草案和历史验收混在一起。

## 3 范围与依赖顺序

### 首版范围

- 社区开发预览保留四类已开放能力；Python 插件仍使用现有私有环境和 Runner 或原生 MCP 机制。
- 首版商店只收录经过公开审核清单检查、在支持环境完成验收的具体 wheel。每个版本分别审核，不根据作者名或源码仓直接授予资格。
- 首批 wheel 仅接受 `py3-none-any`，允许 Python 源码和声明的资源，不含原生模块或可执行二进制；文件名、WHEEL 元数据和实际内容都要检查。版本仅接受无前导零的 `X.Y.Z`，不接纳预发布、开发版或 `+build` 后缀。这是目录首版限制，不缩小现有本地安装的协议范围。
- 首批目录包不声明第三方 Python 运行依赖，或者仅声明与 Host 自带版本兼容的 SDK。标准库实现的 TTS、MCP，以及数据主题、Skill 均可参与。
- 当前带第三方依赖的本地安装能力保留。例如 Fish Audio 可继续通过现有方式使用，但其 websockets、msgpack 依赖未解决商店交付规则前，不进入首批目录。
- Skill 或 MCP 即使使用资源包，也可能执行脚本或命令；“安装时不执行代码”不表示“运行时没有执行风险”。首版目录 MCP stdio 启动限于 Host 提供的 `${python}` 和包内已审核脚本；Windows 参考方式为 `${python}` 调用包内模块或 `.py`。启动参数和包内实现必须符合第 8 节审核规则，不能用 npx、uvx、pip 或脚本在运行时下载执行未经审核的代码。
- 初始桌面资格目标为已验证的 Windows 路径；跨平台静态与进程测试继续保留，不据此宣称完整 Linux/macOS GUI 支持。
- 离线本地 wheel 安装继续可用；关闭商店或目录服务不可用时，已有插件管理仍可用。

自动更新、热重载、任意目录开发模式、SDK PyPI 发布、评分评论、账号系统、付费、遥测、通用依赖锁定、自动回滚、网页扩展、ASR、可安装 AUIP、记忆与形象包均不在首版范围。

## 4 D0 收口公共契约与作者入口

**要补什么**

1. 将当前支持范围、作者快速开始、历史验收分开。Host profile 顶部保留简洁当前契约，历史探针和审计移到独立历史资料并保留原引用的可追溯入口。
2. 说明应用版本、Host API `0.1`、各贡献 contract `/v0`、SDK `0.1.0` 的不同含义。Host 版本不能直接当作 SDK 兼容范围。
3. 发布一张来自现有 profile 的支持表，列出接入 owner、选择或绑定方式、生效时机、测试平台和限制。
4. 修正协议仓“尚未合并”的状态与 Host ROADMAP 中已经完成的安装管理描述；把本计划范围内的精选远程目录、商店式发现移到当前方向，将包签名、自动更新、回滚继续留在 Later。写清 Settings 中仍可访问管理器；本次留档不直接改 ROADMAP。
5. 明确预览期兼容性：契约变化通过版本、来源 pin、变更说明和迁移方案表达，不悄悄改变已有 contract 的含义。
6. 在作者入口区分“符合包协议”“当前 Host 能运行”“首版目录收录”三个结论，链接第 16 节的责任划分。新增类型的流程由真实调用方、原生 owner 和合约验收驱动，不承诺修改一个枚举即可开放。

**改哪里**

- Host：`docs/extension_host_profile_v0.1.md`、`examples/extensions/README.md`、`README.md`、`README_ZH.md`、`ROADMAP.md`、`CONTRIBUTING.md`。
- 拟新增 `docs/extension_authoring.md` 作为唯一作者入口，链接现有规范与示例，不复制全部协议。
- 协议仓：`README.md`、`sdk/python/README.md`、`spec/extension-protocol-v0.1.md`；跨仓引用优先指向已发布或固定的版本。
- 如调整规范或 SDK 来源文件，先在协议仓完成，再更新 Host pin；不能为改文案直接编辑受 pin 管理的 Host 副本。

**验收标准**

- 作者从主仓或协议仓首页均能到达同一条当前作者路径，无开发分支链接依赖。
- 表格中的开放类型与 `profile.json` 相同；明确区分 Schema 合法、Host 接受、运行健康、真实服务资格。
- 新作者能判断：自己的能力属于哪类、是否需要 SDK、在哪配置和绑定、何时生效。
- 明确作者静态检查、示例构建与实际 Host 安装所需的不同环境；静态检查不要求完整 Host 依赖、GPU 或角色资源。
- 本阶段只改变文档，不宣称已完成 D1 至 D3。

## 5 D1 整理统一作者校验入口

**要补什么**

先把已有 `tools/extension_package.py` 整理成对外有文档的目标 Host 校验入口，复用 `validate_manifest`、`inspect_wheel`、`validate_config`、`validate_installed`。作者取得固定 Host 源码快照后，可在最小检查环境中使用工具，不必安装完整 Host。首版不要求作者工具成为独立 PyPI 产品。

静态检查的直接依赖为 jsonschema、packaging、PyYAML；在 `pyproject.toml` 声明 `extension-authoring` 依赖组，从同一份 `uv.lock` 用 `uv export` 生成带哈希的 `tools/requirements-extension-authoring.txt`，CI 比对导出结果，固定全部传递依赖而不维护第二份锁，使用 `pip --require-hashes` 安装。示例构建另列所需构建工具，实际运行和 GUI 使用 Host 支持的环境，不能把静态检查环境描述为完整执行环境。

当前 `inspect_wheel` 按运行解释器的平台和 Python 版本准入。首版目录 CI 固定使用 Windows runner 与 CPython 3.12.10，固定包含 D1 的 Host 校验器 commit、协议 pin 和检查依赖锁，不跟随浮动 main。首次可用 pin 由 D1 完成后记录；后续升级必须重新验证。暂不增加目标环境模拟参数；其他系统上的作者会得到本机准入结果，Windows 资格由固定 CI/实机给出。

保留内部 helper 的 JSON/stdin 行为，避免破坏 Electron 调用。需要面向人的结果时增加显式输出选项，默认机器协议保持兼容。输出指出目标 Host/profile、检查范围、失败位置与原因；不输出密钥值。必要的新静态能力放回现有 owner，不在 CLI 重新实现一套规则。

分清三层结果：

- 协议结构与语义：使用协议仓的 schema/validator。
- 指定 Host 的包、SDK、平台与配置准入：使用 Host 的 `package.py` 和 `profile.py`。
- 字体可用性、原生图像解码和主题绘制对比度：需要目标 Electron 环境验证，静态 CLI 不代替这层验收。

**改哪里**

- `tools/extension_package.py`：作者输出、帮助、检查范围说明；已有命令优先复用。
- `server/extensions/package.py`、`profile.py`、`sdk.py`：只补目标 Host 所需的公共检查结果，避免把 Electron 运行环境规则迁入静态验证器。
- `tests/test_extensions.py`、`test_extension_resources.py`、`test_extension_sdk_build.py`：复用有效和无效包用例。
- 拟新增 `tests/test_extension_authoring.py`：验证作者入口与 Host helper 对同一输入结论一致。
- `pyproject.toml` 的 `extension-authoring` 依赖组与 `uv.lock`：唯一解析来源；`tools/requirements-extension-authoring.txt` 为带哈希的派生导出，CI 检查漂移。
- `docs/extension_authoring.md`：文档化现有命令及新增选项，明确静态检查不执行包。
- 协议仓只有在发现实际重复规则时才抽取共享静态规则；遵守规范来源与许可归属，不能把 Host AGPL 代码直接改标为 Apache-2.0。

**依赖与验收**

- 依赖 D0 确定的支持范围；不依赖商店或开发目录模式。
- 对同一 wheel，`check-wheel` 与安装 helper 的静态准入结论一致；`check-package` 只承诺清单与资源检查，不具备 wheel 元数据，必须将入口点、清单/wheel 版本一致性和 SDK 依赖列为未检查，并提示安装前运行 `check-wheel`。
- 用 SDK 要求不兼容、版本不一致和入口点不匹配的 wheel 验证上述边界：源码可以通过已声明范围，但 wheel 检查必须与安装器一致拒绝；错误的源码目录应提示缺少 `amadeus-extension.json`，不能冒称校验器不可用。
- 该一致性指相同目标 Host 下的通用包检查；目录首版政策另行判断。一个被当前 Host 正常支持、但因第三方依赖等原因不满足首版目录政策的包，仍应通过原有本地准入，目录拒绝原因须明确来自收录政策。
- 干净最小环境能完成所有静态检查，不导入模型、音频或 Provider 运行时；锁文件可复现安装。`platforms: ["win32"]` 的有效包在固定 Windows CI 通过，在其他平台报告实际不兼容，不能被通用 Linux 收录任务误拒。
- 覆盖未知贡献、非空 Host 权限、SDK 不兼容、清单与 wheel 身份不符、错误配置类型、缺失资源、危险归档路径及 `.pth`。
- 恶意 `__init__.py` 哨兵在静态检查时不执行；网络不被调用；凭据不进入输出。
- 某项原生检查未运行时，报告该项待目标环境验证，不能给出“整个插件通过认证”。
- 未新增权限、插件扫描、环境自动安装或隐式 pip 调用。

## 6 D2 提供模板与可运行合约检查

**要补什么**

用现有六个示例整理四条作者旅程：TTS、MCP、Skill、主题。保留示例作为可构建包，文档说明必须修改的包 ID、Python distribution、版本、entry point、贡献 ID、许可和配置。第一批用合成音频和本地服务验证，付费服务资格单独记录。

在 Host 的作者工具旁提供一个显式运行的合约检查脚本，拟名 `tools/check_extension_contract.py`。静态验证与执行检查是不同命令；执行检查会启动所选择的可信测试包，应在独立临时环境中运行，不借用用户正在使用的配置或 Agent 会话。

| 类型 | 最小可执行检查 | 必须验证的失败结果 |
| --- | --- | --- |
| TTS | initialize/ready、清单注册一致、一次流式合成、取消、关闭 | 错误握手、未声明语言、非法音频、超时、取消后迟到音频；失败请求不重放 |
| MCP | 本地 stdio 或受控 HTTP 服务发现、一次合成数据调用、关闭 | 凭据不能进入 argv/URL、错误 Provider 绑定、启动失败；不回退到 Host 全量环境 |
| Skill | 清单与资源有效、指定 Agent 发现、一次资源读取、会话恢复 | 资源缺失或遮蔽、修改/移除已记录修订后拒绝旧会话；新增无关 Skill 不误伤旧会话 |
| 主题 | 静态包检查，目标 Electron 解码、绘制和切换 | 无效颜色/图片、对比度不足、更新失败、内置主题恢复；纯主题不启动 Runner |

报告分开列明静态、合约进程、Agent 原生、GUI、远程真实服务各层结果。合约工具不模拟一个“万能 Host”，也不以受控模型证明真实模型选择质量。

**改哪里**

- `examples/extensions/` 六个现有示例及 README；规范侧示例继续作为清单参考，避免两边都维护相同完整实现。
- 拟新增 `tools/check_extension_contract.py` 与对应工具回归；复用生产 Runner/MCP/Skill 接口及现有 fixture，避免将测试私有实现变成公共 SDK。
- `tests/test_extensions.py`、`test_extension_examples.py`、`test_extension_fish_audio.py`、`test_extension_mcp.py`、`test_extension_skills.py`。
- `tests/test_skill_codex_runtime.py`、`test_skill_pi_runtime.py` 与 `tests/test_pi_mcp.py`：原生适配器资格。
- Pi/MCP 相关命令在包含 #234 的干净目标主线运行，连同该主线的精确调用授权回归一起记录；不能复用当前工作区结果作为这条资格。
- `tools/probes/extension_theme_lifecycle.py`、`electron/tests/extensionsInstall.smoke.mjs`、`extensionThemeNative.smoke.mjs`、`extensionSettings.smoke.mjs`：安装与主题实机层。
- `.github/workflows/` 现有 Python/Electron 工作流：加入最小离线作者旅程，不让每个静态检查依赖完整 GUI。

**验收标准**

- 每类至少一个参考包在独立环境完成构建、静态校验和对应最小合约检查。
- TTS 示例使用交付给用户的固定 SDK wheel，不依赖另一棵未发布源码。
- 至少覆盖一条 MCP 与一条 Skill 的真实 Provider 路径；其他 Provider 按各自已有测试和限制列出，不统称全部认证。
- 安装、更新、卸载测试复用现有 installer/store；新工具不能仅通过绕过安装器的内存 fixture 宣称端到端成功。
- 错误用例使工具以非零状态退出；报告可定位哪个阶段失败。

**诊断日志的处理**

当前 `RunnerClient._stderr` 只排空 stderr。D2 先提供握手阶段、状态、退出码和超时等受控诊断，不承诺保留任意插件日志。若 D3 作者因诊断不足无法完成旅程，再单独补默认关闭、短期、有大小限制的日志功能；必须明确敏感数据边界、删除方式和测试。通用目录挂载与自动重载继续延后。

## 7 D3 完成外部作者验收

**目标**

至少两位未参与底座实现的作者，各自在独立源码仓完成一个插件。其中至少一个使用进程能力，另一个使用资源能力；两者合计覆盖至少两类贡献。优先按第 3 节目录范围选型，便于以后收录，但不要求作者公开发布包。四类参考模板均须完成 D2，不要求首轮四类都有外部作者。

**旅程**

1. 作者只从公开作者入口开始，创建自己的身份和包，不修改 Amadeus 核心。
2. 构建 wheel，运行校验与合约检查，安装到独立用户配置。
3. 配置、启用、选择或绑定，完成一次有意义的调用。
4. 发布本地第二版本，验证更新披露、生效时机和既有配置保留。
5. 停用、卸载、重装，分别验证默认保留数据和明确删除数据。
6. 记录文档缺口、兼容性问题、诊断困难和实际所需依赖。

**改哪里与依赖**

- 依赖 D2。作者源码保留在作者自己的仓库；贡献不默认转移进 Host。
- `docs/extension_authoring.md`、`examples/extensions/README.md` 按实际反馈修正。
- 拟新增 `docs/verification/extensions/community-preview.md`，记录作者同意公开的包、Host/SDK 版本、平台、命令、成功和失败结果。
- 必要修复回到对应 owner，不能为了某个包增加永久 ID 特例或扩大 Host 权限。
- 邀请、公开消息与作者包发布属于后续明确授权的协作动作，本计划不自动执行。

**退出条件**

- 两个外部包完成上述全流程；只有复制模板或能启动不算完成。
- 作者可以只授权本地验收和脱敏结论记录；公开源码、wheel 或加入目录需另获作者同意。维护者参考包不能充当这两个外部成果。
- 没有依赖未记录的本地补丁、维护者手动改配置、个人绝对路径或未发布 SDK。
- 关键阻塞已经修复并回归；剩余限制进入作者说明。
- “社区开发预览”仅承诺已验证子集，稳定 SDK 和新贡献类型继续另行评审。

## 8 S0 确定精选目录与收录规则

**依赖与发布位置**

依赖 D1，不依赖 D3。先使用已有参考包和测试 fixture 验收。目录源放在 Amadeus-Extensions 的 `catalog/`，首版选择受保护 main 上的 `catalog/index.json`，通过官方 raw HTTPS 地址分发，不另外部署 Pages 或 Release 索引资产。

目录输入先经审核合入 main。发布 PR 选定一个已合入的输入 commit，固定生成器和 Host 校验器版本，生成索引并提交审核。生成时间取该输入 commit 的时间，不读取构建机器当前时间；相同输入和工具版本生成相同字节。索引记录输入 commit，避免把包含生成文件自身的 commit 当作输入造成循环。

发布序号是版本库中的显式递增整数，每次发布相对当前 main 已发布索引加一，重复构建不增加。发布 PR 合并前重新验证序号和当前状态；并行 PR 发生冲突必须更新后重审。回退目录内容也使用更大的序号，并保留既有封禁或显式解除记录，不能恢复旧序号文件。不用时间戳或 Actions 运行次数代替发布序号，不允许发布机器人绕过分支保护直接推 main。

**条目输入与生成结果**

| 维护方式 | 信息 | 规则 |
| --- | --- | --- |
| 手工提交并审核 | wheel 精确 URL、SHA-256 | 每一份待审核产物有确定字节；初始源可使用 GitHub Release 的具体资产 |
| 手工提交并审核 | 发布者对包 ID 的归属证明、维护权转移记录 | author 文本和 PR 账号不能单独自证所有权；支持组织与代理提交 |
| 手工提交并审核 | 审核人、清单版本、日期、证据及绑定的产物摘要 | 每个版本重新审核，不能继承前一版本的资格 |
| 手工提交并审核 | 撤回原因、安全封禁或显式解除决定 | 区分维护者撤回、版权/素材授权下架和安全封禁 |
| 从 wheel 生成 | 包 ID、版本、作者、许可、主页、说明、源码仓 | 读取 manifest 和 metadata；不要求提交者再填一份 |
| 从 wheel 与固定检查环境生成 | Host API、平台、Python、SDK、依赖、贡献与启动声明、文件大小 | 复用 D1 检查，不创建可漂移的第二份清单 |
| 从发布输入生成 | 格式版本、发布序号、输入 commit 及其时间、校验器 pin | 使发布可追溯、可重建 |

包清单不新增商店字段。生成器校验人工事实与产物身份的绑定，但不再要求作者手写能从产物推导出的元数据。客户端以安装记录已有的 `id + version + digest` 查询目录并投影审核状态，不新增持久化分发来源或信誉等级。

目录格式使用可独立解析的展示与兼容性摘要；其中贡献的 kind、role、contract 等来自实际产物，但读取目录不调用客户端的完整插件 manifest 校验器。新增贡献值不应迫使目录格式升级。哪些可选信息字段可忽略、哪些字段决定安装资格和安全语义，由 `catalog/schema.json` 与说明明确规定；旧端不能理解的必需语义必须阻止相应安装，不能当作可忽略展示字段。格式与条目兼容规则见第 16 节。

**公开审核清单**

拟交付 `catalog/REVIEW_CHECKLIST.md`。审核对象必须是目录 SHA-256 对应的 wheel 解包内容；源码仓、构建说明和源码对照是辅助证据，不能替代产物审核。目录中的“已审核”表示该具体产物按某版清单完成检查，不是安全保证，也不扩大权限。

| 检查项 | 自动检查与人工检查 |
| --- | --- |
| 产物身份 | 校验 SHA-256、包 ID、版本、metadata、entry point；保存文件清单。版本仅为无前导零的 `X.Y.Z`，清单与 metadata 字符串一致；同一 ID/版本不可替换字节 |
| wheel 格式与内容 | 文件名和 `.dist-info/WHEEL` 均须为 `py3-none-any`，并声明 purelib；拒绝 `.pyd`、`.so`、`.dll`、`.exe`、`.dylib` 等原生载荷和已知可执行二进制。检查异常内容/签名与源码可审查性，不能只信标签或扩展名；主题图片等合法资源按原契约检查 |
| 静态 Host 准入 | 使用固定 Windows/CPython/Host pin，检查支持类型、配置、SDK、路径、资源及 `.pth`；保留正反 fixture |
| 依赖 | 目标环境有效依赖为空或仅为兼容 Host SDK；不含第三方运行依赖、直接 URL、源码构建或隐式安装步骤 |
| 启动命令 | MCP stdio 只允许 `${python}` 或 `${package}/` 内已审核脚本。`${python}` 的模块必须属于包，脚本必须位于包内；拒绝 `-c`、`-m pip`、任意配置值充当可执行目标，以及 npx/uvx 等运行时获取代码的入口。包脚本须证明在声明平台可执行，Windows 优先使用 `${python}` 加包内模块/`.py` |
| 运行内容 | 审核入口、脚本、Skill 指令和网络使用；拒绝下载后执行代码、隐藏安装器或绕过声明的命令。允许声明的远程服务调用，但网络响应不能被当作代码执行；人工审核不是 OS 沙箱 |
| 权限与数据 | 核对实际文件/网络行为与披露、凭据处理、数据保留和删除；不授予 Main Chat 或新 Host 权限 |
| 素材与许可 | 代码许可与包内图片、音频及其他素材授权分别可核对；记录来源、许可或作者授权。当前主题只引用已安装字体，审核不代表开放字体分发；以后如包含字体等素材仍需单独证明授权 |
| 生命周期证据 | 完成该类型所需的安装、调用、更新、取消/关闭和卸载检查，注明环境与未验证范围 |
| 版本差异 | `check_catalog.py` 对比上一已审核版本，输出新增/删除/修改文件、文本差异、二进制摘要与清单/依赖/命令差异；每个版本仍完整过清单，差异只用于辅助审查 |

维护者自己的参考包也需遵循同一清单，并由非作者本人评审。初始包没有前一版本时输出完整清单；未知格式或无法审查的内容不给“已审核”状态。

**信任与网络规则**

- 索引只认一个内置官方 HTTPS 来源。首版不做签名，因此信任根落在官方 GitHub 仓库及发布权限；S3 必须落实对应治理条件。索引镜像要等签名和密钥管理完成后再开放。
- 允许用户在 Host 设置中配置产物镜像。镜像只替换下载位置，不能提供新的身份、摘要或审核事实；产物仍与官方索引逐字节校验。
- 下载与重定向不硬编码 GitHub CDN 域名；逐跳限定 HTTPS、无 URL 用户名/密码、重定向次数、超时和体积。不携带应用会话 cookie/凭据，不允许 renderer 提交任意可信下载地址。
- 静态检查可以处理未信任 PR，但生成器、工作流和 Host 校验器来自固定可信版本。合约执行只在维护者批准的隔离、无凭据环境中进行，不使用有发布或仓库写权限的任务执行投稿代码。
- 维护者撤回和版权下架停止目录新安装与更新推荐；安全封禁还阻止已知产物后续激活。版权下架不自动变成安全封禁，也不静默删除用户已有内容。

**改哪里**

- 协议仓拟新增 `catalog/packages/`、`catalog/schema.json`、`catalog/README.md`、`catalog/REVIEW_CHECKLIST.md`、`catalog/index.json`、`tools/check_catalog.py`、`tools/build_catalog.py` 及对应测试。
- 固定 Host 校验器 commit 和 D1 的最小依赖锁；复用协议 validator、规范 fixture 和指定 Host 入口，目录收录规则保持独立于一般本地安装准入。
- 首版纯 Python、版本格式、依赖和命令限制集中在目录收录政策与公开清单中，不写成所有插件的永久运行条件。客户端需要复核的目录交付限制使用同一政策定义/一致性 fixture，不能在 renderer、Runner 和 Provider 各维护一份允许列表。
- `.github/workflows/validate.yml` 增加 Windows 收录检查、wheel 内容差异和索引重建比对；发布 PR 使用受保护 main 的审核流程。
- Host 侧此阶段只确定消费契约，不增加用户可见商店入口。

**验收标准**

- 合法主题、Skill、标准库 MCP 和 SDK TTS 参考包可以生成目录；`platforms: ["win32"]` 的包不被 Linux 环境误拒。
- 错摘要、内部身份不一致、错误 wheel 标签、原生载荷、非 `X.Y.Z` 版本、归属不明、未审核的新版本、额外依赖和下载执行命令不能收录。
- 元数据均从实际产物生成，修改 manifest 后不需要维护另一份重复描述。审查明确覆盖实际 wheel 与上一版本的差异。
- 同一输入和工具 pin 重建得到相同索引；并发发布、重复序号、旧序号和同版本换字节被拒绝，回退内容仍保持发布序号递增。
- 发布流程不能执行未审核投稿代码；维护者参考包不能绕过审核。版权下架、普通撤回、安全封禁及解除均有 fixture 供 S1 使用。
- 用“当前兼容包 + 未知未来类型 + 已知类型的新 contract + 混合贡献包”的目录 fixture 验证第 16 节行为。生成器仍只发布其固定 Host 已验证的生产类型；未来 fixture 不修改生产 profile，也不作为真实新类型已获支持的证据。

## 9 S1 将可信目录接入现有安装器

**责任分配**

Electron main 获取、校验目录，持久提交安全事实后更新展示缓存，下载 wheel，并把可信的预期身份和摘要交给现有安装器。Renderer 只提交包 ID、具体版本和用户动作，不提交可信 URL、等级或期望摘要。Python 后端继续消费 Host 已校验的启动快照，不增加第二个联网目录客户端。

沿用 `StoredExtension.id/version/digest` 匹配目录，动态得出“目录收录”“已审核”“已撤回”等展示结果。不新增安装来源或等级字段，也不设置本地包转商店包的接管流程。同一份字节经过两个入口安装应有相同身份与准入结果；本次操作的实际下载地址可用于确认披露，不作为长期信任依据。

**拟新增与修改位置**

| 位置 | 修改职责 |
| --- | --- |
| 拟新增 `electron/src/main/extensionCatalog.ts` | 获取目录、格式校验、逐条兼容性判断、审核投影与展示缓存；通过现有 store 提交安全事实 |
| 拟新增 `electron/src/main/extensionDownloads.ts` | 使用 Electron net 的有界下载、镜像、取消和失败清理；不拥有安装或配置状态 |
| `electron/src/main/extensions.ts` | `install` 接收可选可信交付元数据；复用复制、inspect、确认、准备、提交与清理；在启动及前端准入检查已知封禁 |
| `electron/src/main/desktopSettings.ts` | 复用 fsync、原子替换及 `.bak`，保存已知封禁与已接受最大发布序号；补安全事实的损坏/恢复边界，兼容旧设置 |
| `electron/src/shared/extensions.ts` | 商店摘要、动态审核/安全状态与操作结果类型；不增加持久化分发来源或传递凭据 |
| `electron/src/main/index.ts`、`preload/index.mts`、`renderer/env.d.ts` | 受限目录查询、安装、取消和安全刷新 IPC；主进程校验外链后打开浏览器 |
| 现有配置目录、设置存储及界面 | 产物镜像设置复用现有设置体系，不引入第二份配置文件；不提供索引镜像设置 |
| `server/extensions/package.py`、`sdk.py`、`runtime.py` | 静态依赖分类复用 packaging 与当前 marker 语义；启动拒绝仍由已有 owner 处理 |
| 拟新增 `electron/tests/extensionCatalog.test.mjs`、`extensionDownloads.test.mjs` | 目录、下载和可信输入边界 |
| `electron/tests/extensions.test.mjs`、`desktopSettingsDurability.test.mjs` 及作者工具测试 | 两入口一致性、依赖分支、断电恢复、更新与撤回集成 |

新增文件名是建议落点，开工时可以按实际职责收敛；已有 installer/store 仍是唯一安装与状态 owner。

**必须保持的行为**

1. 下载使用 Electron `net`/Chromium 网络栈，继承受支持的系统代理与证书验证，不关闭证书检查。使用不携带应用会话凭据的请求；每次重定向均检查 HTTPS 和无 URL 凭据，限制跳转数、超时和体积。不要依赖 `net.fetch` 的 `integrity` 选项，它不会执行该校验；摘要由后续安装器显式验证。系统代理、证书拒绝和镜像分别验收。
2. 下载在 Host 管理的暂存目录完成，有取消和失败清理；异常不提交记录，也不进入 pip。wheel 上限复用当前检查边界，不创建无限缓存。镜像只提供字节；地址与目录摘要的绑定由 main 处理。
3. 安装器先复制为受控字节，再用现有检查得到摘要和清单；与目录的预期包 ID、版本、摘要逐一比较。只在下载层算一次 hash 不足以建立安装事务的身份。
4. 目录准入、依赖限制和已知封禁在安装与提交前重新核对。用户等待确认期间发生目录变化或包状态变化，不能提交已经失效的授权对象。
5. 按 wheel 内容选择准备方式，而非按入口选择。`runtime.kind=none` 继续直接解包；Python wheel 的目标环境有效 `Requires-Dist` 为空或仅为兼容 SDK 时，两个入口均在准备固定 SDK 后用 `--no-index --no-deps --only-binary=:all:` 安装。仅本地入口允许带第三方依赖的包进入现有依赖解析分支。依赖分类在静态检查 owner 完成，兼容环境 marker，不在 Electron 另写一套解析规则。
6. 旧安装记录不做来源迁移；以现有三元组精确匹配目录。目录无匹配时显示“未收录”，目录不可用或缓存过期则如实说明审核状态未知/截至上次检查，不能宣称当前安全。持久封禁始终独立检查，缺目录不能解封。
7. 更新继续调用相同安装事务；新包准备失败保留旧版。配置保留、混合包重启和 Skill 旧会话失效规则不变。不额外按本地/商店身份建立更新所有权。
8. 不承诺启动失败自动回滚。旧后端退出后新版本不能启动时，保留明确错误与管理入口，允许停用、卸载或安装允许的修复版本；降级还需作者说明数据兼容性。
9. 目录可展示不等于安装可执行。main 在安装入口重新检查本机对包内全部贡献及其 contract、交付方式和依赖的支持，随后对实际 wheel 做既有完整准入；renderer 绕过禁用按钮也不能安装。不认识的贡献不被删除、重写或自动映射到 TTS Runner，混合包不能只安装其中“认识的部分”。

**安全事实持久化与恢复**

- 已知封禁和已接受的最大发布序号属于 Host 耐久事实，放进现有设置存储；目录缓存只负责展示，不承担防回退或启动授权。二者在同一次持久提交中更新，提交成功后才公开新目录结果；失败保留旧事实，不能只更新序号或先宣称刷新成功。
- 复用现有主文件、`.bak`、fsync 与原子替换。恢复安全事实时识别主副本中最高完整序号对应的安全快照，不能仅因主文件可解析而忽略副本中更高的已持久事实；同序号但内容冲突视为不可用，不逐字段拼凑。普通设置与凭据保持现有恢复职责。
- 旧版有效设置中不存在安全字段，按尚未取得目录状态迁移；字段存在但损坏、主副本均被 NUL 填满/截断、或已接受的安全事实无法恢复，不能等同于空封禁。此时暂停新的扩展安装和激活，关闭前端扩展准入，已运行后端按既有停止边界提示处理；保留内置功能、卸载和恢复入口。
- 当前 `read()` 在无法解析且无可用副本时会隔离文件并返回空设置。S1 必须让安全事实的不可恢复状态持续可见，不能被下一次普通设置保存或重启清空；保留损坏证据，普通设置恢复不能静默宣布插件已解封。修复使用可恢复副本或显式重新取得官方安全状态，记录这是恢复操作，不承诺抵抗用户主动删除全部本地状态。
- 低于已接受序号的索引拒绝；相同序号只允许一致的安全事实和展示缓存重建；更高序号才能改变安全决定。封禁不因目录缺项、缓存删除、普通卸载/重装或网络失败消失，解除必须是更高序号中的明确决定。
- 条目兼容性不能改变安全事实的解析：未知贡献类型的条目可标为不兼容，但同一索引中有效的封禁/解除仍须按既有事务处理。目录格式主版本或安全语义无法理解、身份冲突或安全结构损坏时拒绝整份新快照，保留旧安全事实和最高序号，不把局部兼容处理当作忽略安全错误的理由。

**联网覆盖与撤回处理**

- 打开“浏览”、显式刷新，或在“已安装”视图点击“检查更新与安全状态”时联网；首版不自动在启动时检查。显示最后成功检查时间和失败原因，从不检查的用户无法获知新的远程封禁，这项取舍在第 14 节明确保留。
- 网络失败使用已存安全事实；展示缓存缺失/损坏不改变封禁或序号。安全存储有效时，本地安装和已有插件管理可离线使用；无目录时浏览不可用。安全存储本身不可恢复时按上一小节处理，不能以离线模式绕过。
- 普通撤回或版权下架阻止目录新安装与更新推荐，不自动停用或删除已安装版本；它们不是本地执行封禁。安全封禁按包 ID、版本和摘要识别，同时覆盖本地与商店入口。
- 安全封禁阻止下一次后端激活，并立即关闭对应前端贡献；已运行后端明确显示需要重启/停止，遵循已有进程退出与引用清理边界，不假报已经停止。
- 处理时同时检查期望版本和实际加载版本。例如已保存安全 v2、仍运行封禁 v1，仍须显示旧后端待停止；已运行安全 v1、待启用封禁 v2，则拒绝 v2 激活。
- 封禁不静默删除包数据、凭据或用户启用意图；UI 显示政策阻止原因。继续复用启动拒绝与前端准入 owner，不引入通用热协调协议。

**验收标准**

- 正确包完成下载、校验、确认与安装；同一文件走本地/商店入口时准备方式、身份、审核投影及生命周期结果一致。无依赖/仅 SDK 的本地包也不访问 pip 索引。
- 摘要不符、身份不符、超限、断网、取消、无权限、错误重定向、不支持的依赖和 SDK 版本均不留下已安装成功状态；合法第三方依赖仅从本地入口走现有解析路径。
- 系统代理、正常证书验证、无效证书拒绝、镜像正确字节/错误字节、HTTPS 重定向/降级及请求凭据隔离有明确测试，不依赖某个 CDN 主机名。
- 模拟下载后替换字节、确认期间封禁、并发更新/卸载，拒绝过期对象且不删除仍被引用的环境。
- Renderer 伪造 URL、等级、来源或另一版本不能绕过 main 的解析和授权。
- 旧设置兼容且不添加来源字段；配置/凭据/绑定不丢失。缓存损坏或删除不改变封禁；安全记录主损坏、副损坏、双损坏、NUL、截断、写入两文件之间失败、更高序号只存在副本、重启及普通设置保存均不能静默解封。
- 首次取得目录、旧版有效记录迁移、同序号冲突、旧索引重放、显式恢复、离线、普通撤回、版权下架、安全封禁、解除及 desired/applied 版本不同的情况都有正反测试。
- 普通卸载/重装、从本地选择相同已知封禁产物不能绕过；不承诺识别修改字节后产生的未知产物，首版封禁范围明确为三元组。
- 本地安装和安装后保持禁用的默认行为不因商店接入改变。
- 第 16 节的旧端兼容矩阵全部通过：未知类型/contract 只阻止对应包，兼容条目仍可浏览和安装；混合包整包拒绝且没有部分提交；未知类型出现时合法安全更新照常持久化。未知目录格式主版本或损坏安全结构不提交新序号、不覆盖旧事实。

## 10 S2 完成商店用户旅程

**界面范围**

在现有插件管理器中增加“已安装”和“浏览”视图。首版提供名称/能力搜索、类型筛选、详情、版本兼容原因、安装、下载进度与取消、手动刷新和手动更新。“已安装”视图提供“检查更新与安全状态”，显示最后成功检查时间；用户无需进入浏览页才能取得安全状态。不新增独立插件管理页，不要求恢复侧边栏 Plugins 才能使用。

详情显示维护者、许可、产物地址、审核范围、所需平台/运行环境、外部服务或命令、下载体积及生效方式。审核信息按具体产物匹配，并带上目录检查时间。下载体积只包含实际可核对的 wheel/交付内容，不能冒称包含外部服务或未安装运行时。

目录说明、作者名和其他第三方文本首版只按纯文本显示，不渲染 HTML/Markdown，也不加载远程图片。主页和源码链接由主进程确认是无 URL 凭据的 HTTPS 后，在用户点击时交给外部浏览器；不能直接将目录字符串传给 shell 或导航当前窗口。素材授权下架与安全封禁使用不同原因文案。

安装前沿用现有原生披露；安装成功后引导用户到配置、启用、Agent 绑定、Voice 或 Appearance。显示“已下载”“已保存”“待重启”“实际生效”“被阻止”的真实区别。审核标记不替代安装与执行确认。

**改哪里**

- `electron/src/renderer/components/ExtensionSettings.tsx`：复用列表、编辑与操作反馈。
- 拟新增 `ExtensionCatalog.tsx`：浏览与详情；组件只消费受限 main 返回的数据。
- `extensionSettingsCatalog.ts`、`SettingsPage.tsx`：兼容性呈现、导航与草稿保护。
- `electron/src/shared/extensions.ts`、`renderer/env.d.ts`、`preload/index.mts`：界面所需公开数据和方法。
- `electron/src/renderer/locales/zh-CN.json`：完整中文文案；沿用现有英文来源。
- `electron/tests/extensionSettings.test.mjs` 和实际组件/导航 smoke：加入浏览、取消、失败与更新旅程。

**验收标准**

- 用户可在一个管理器中发现、安装、配置、启用、使用、更新、停用和卸载一个包。
- 无兼容版本说明具体原因；未知类型、SDK 不兼容和平台限制不能只显示为通用“安装失败”。
- 同一目录存在未来类型时，显示可安全读取的名称、类型与不兼容原因，关闭该版本的安装/启用入口；兼容条目的搜索、筛选、详情与安装不受影响。新版本不兼容时保留已有正常版本，不推荐该更新；若仍有允许安装的较新兼容版本，可推荐该版本。
- 有更新仅代表存在可安装的较新 `X.Y.Z` 版本，按三个非负整数比较，不按字符串排序。非目录格式的已有本地版本继续可管理，但不猜测与目录版本的升级关系；用户可查看具体候选并走显式安装确认。首版不提供预发布规则或开关。
- 商店刷新失败不清空已安装列表，不丢未保存配置，不把旧成功提示留在新失败操作之后。
- 双击安装、切换视图、取消下载、更新失败、后端离线都不会误报完成。
- 新装、更新、审核状态变化、版权下架、封禁及安全状态不可用提示覆盖中英文、窄窗口和键盘操作。
- 含 HTML、脚本、Markdown 图片和危险链接的目录文本只能呈现为普通文字；远程图片不发请求，非 HTTPS/带凭据外链在 main 被拒绝。
- 不进入浏览页的用户可以在“已安装”检查安全状态；离线和安全存储损坏显示不同原因，不能把“未检查”显示成“安全”。
- 纯主题即时生效、混合包待重启、卸载数据选择、主题原生恢复仍通过现有旅程。

4. 每条证据记录 Host commit、构建产物摘要、目录 revision、插件版本与摘要、SDK pin、平台和使用方式；自动化驱动确认与人工原生确认分开。
5. 维护者可通过目录 PR 撤回测试版本；客户端刷新后准确反映，离线时保留已知封禁。回滚目录发布不能无声抹去已知封禁。
6. 当前目标主线的必要 CI 与作用域回归通过，GUI 截图和失败证据可审查。跳过项明确列出，不能当作通过。
7. 发布前确认目录维护责任、审核范围、问题接收与撤回流程。公开发布是独立动作，不能由测试通过自动触发。

9. D3 完成后才能结案为经过外部作者验证的社区预览。D3 尚未完成而 S2/D2 与技术发布检查均完成时，可另作技术预览发布决定，明确未完成资格；不能把维护者包或测试 fixture 替代 D3。
10. 完成第 16 节的政策分离、原生 owner 与旧端兼容验收。首版以固定 reader 和合成未来目录验证；后续扩展以实际上一受支持客户端复验，不能只用修改后的新 reader 测试。新目录类型不得中断旧端兼容包管理或让其漏掉可理解的安全更新。

## 15 第三方依赖的后续路径

此项不进入首版商店，但为 Fish Audio 等包保留明确入口。后续目录按目标 Python/平台锁定完整依赖闭包，逐个记录依赖 wheel 的精确地址、版本和 SHA-256；直接依赖与传递依赖都必须覆盖，不能只固定插件主 wheel。

Host 从原始地址或允许的产物镜像下载这些字节并校验，形成受控本地 wheel 集合和带哈希的 requirements 文件。安装使用 `--no-index --find-links <local-wheel-directory> --require-hashes --only-binary=:all:`，禁止缺项时回到网络索引或源码构建；Host SDK 仍由既有固定交付约束管理。

该阶段需要单独设计目录格式、目标环境 marker、SDK 一致性、依赖许可证与审核范围、下载体积、撤回影响和安装事务的失败清理。依赖集合每次改变都重新审核和验收。它不要求新增包来源字段，也不改变现有安装记录和原生运行 owner。

## 16 新能力接入与旧客户端兼容约束

本节约束首版代码的职责与目录兼容方式，不启动 ASR、网页、AUIP、记忆或其他新类型的实现。现在使用合成未来条目验证边界；真实新增能力以后单独立项。

### 目录收录政策与运行契约分离

| 层次 | 回答的问题 | 所有者与落点 |
| --- | --- | --- |
| 包协议与具体能力契约 | 包如何声明身份、配置和贡献；该能力的输入、输出及生命周期是什么 | 协议仓 schema、contract 与已交付 SDK；Host 通过 pin 消费 |
| Host 支持与安装准入 | 当前版本是否具有对应 owner，是否接受该包的全部贡献、SDK、平台与运行要求 | `server/extensions/profile.json`、`profile.py`、`package.py` 和原生 owner；Electron 使用既有 profile 投影 |
| 目录收录政策 | 当前精选目录愿意分发哪些已支持产物，要求完成哪些审核 | `catalog/REVIEW_CHECKLIST.md`、`check_catalog.py`、固定检查环境及审核记录 |
| 客户端目录展示与交付 | 能否读取条目、是否支持其运行要求和下载/依赖交付方式 | `extensionCatalog.ts`、现有安装器和管理界面；最终校验实际 wheel |

`py3-none-any`、`X.Y.Z`、无第三方 Python 依赖及受限 MCP 启动方式属于首版收录政策。它们不能进入所有插件通用的 manifest 合法性、Runner 调用或 Provider 执行判断中，也不能因为目录放宽就自动改变 Host profile。未来需要原生 ASR 或更复杂依赖时，分别评审该能力契约、Host 消费实现和目录交付政策；没有变化的安装事务与能力不必改写。

通用权限、身份、路径、完整性和取消等已有契约仍适用于所有入口；政策分离不等于从本地入口绕过这些边界或已知封禁。客户端复核首版目录资格的代码集中在目录 owner，复用同一政策定义或一致性 fixture，不能在多个组件复制限制。政策演进通过版本化清单、规范说明和测试表达，不给插件新增“请求放宽政策”的 manifest 字段，也不新增安装记录中的政策授权标志。

**验收标准**

- 选择一个现有 Host 支持、但带第三方依赖的有效包：通用静态检查和本地路径保持原有结果，首版目录因依赖政策拒绝；错误明确区分“目录不收录”与“Host 不支持”。用受控 fixture 验证，不要求付费服务调用。
- 仅改变目录审核政策 fixture，不得改变生产 profile、通用 manifest/SDK 接受范围、TTS 调用、MCP/Skill 权限或本地资源包解包行为。
- “目录已审核”但本机缺少对应 owner/contract/交付能力的包仍不能安装；审核状态不能替代 Host 准入。两入口的通用权限与已知封禁结果保持一致。
- S0/S1 的规则定位检查确认收录限制没有散落在 renderer、Runner、Provider 中；合法与非法案例由目录工具和客户端复核共享，避免两套不同准入结论。

### 新类型由原生 owner 消费

每种新能力按以下顺序接入：

1. 由真实使用场景确定输入、输出、失败、取消、资源释放和权限范围。
2. 指定已有或确有必要新增的原生 owner，明确它如何消费贡献，以及何时停止接受调用。
3. 在协议仓形成最小契约和示例；只有实际执行路径需要时才扩充 SDK 或 wire 方法。
4. 在 Host 接入对应消费者，再更新支持矩阵和生成投影，复用已有身份、配置、凭据、修订、安装和清理事务。
5. 完成该能力正反验收及混合包生命周期回归，最后增加目录类型专属审核项和兼容性证据。

包声明不能选择任意 Python 导入目标作为 Host owner；类型映射仍由 Host 决定。支持矩阵增加一行只表达已经具备的支持，不创建执行能力。ASR 使用识别 owner，主题使用前端资源 owner，MCP/Skill 保持原生协议；不得为了新增类型把 TTS Runner 改成通用插件执行器。可以复用经过验证的进程与 RPC 机制，但不提前增加无人调用的方法、通用回调、热切换或新的授权体系。

**验收标准**

- 首版通过未知类型 fixture 证明没有自动注册、导入、通用 Runner 分派或部分包激活；原四类行为不变。
- 未来真实类型开放前必须同时具备消费者、合约测试、示例和 profile 更新；缺少消费者时保持关闭，不能仅靠清单或目录声明启用。
- 每个新 owner 验证正常调用、无权限/不兼容、取消、故障、禁用、更新和卸载；旧引用释放前不能清理文件，失败请求不因换代重放。
- 新旧贡献组合时继续遵守完整包的修订和生效边界，不在 owner 内新增一套安装记录或绕过混合包重启规则。
- 新类型无启用实例时，原四类能力的注册、路由、执行权和用户旅程通过原有回归。共享基础设施变化必须有新调用方和必要性证据。

### 旧客户端读取新类型目录

S0 的目录 schema 必须把稳定的身份/展示/兼容性摘要与具体贡献的执行细节分开。kind、role、contract 等值可以对旧端未知，浏览时只将它们作为有界文本和不兼容原因，不创建动态代码加载。完整 manifest 仍在安装准入时按本机支持版本校验。

在客户端支持的目录格式内，规范允许的可忽略展示字段可以增加；新增运行必需语义必须能通过既有兼容信息让旧端明确拒绝，无法做到时升级目录格式主版本。不能把未知必需字段伪装成可选字段，也不为兼容旧端删掉新包实际声明的贡献。需要更新的是现有目录 schema、说明和 reader，不另建第二个协商协议。

处理顺序为：验证来源与目录格式 → 完整验证身份和安全结构 → 按现有事务接受安全事实 → 逐条判断本机能力 → 提供安全展示和可安装集合。不支持某条目不妨碍接受可理解的安全事实。格式主版本未知或安全结构不完整时，本次刷新失败，旧有效缓存和安全事实保留，最高序号不前进。

包内任一贡献、contract、必要依赖或交付要求不受支持，就将该版本整包标为不兼容。不得摘掉未知贡献后安装剩余部分。已安装且正常工作的旧版本保持原有状态；更新候选只从仍允许安装且兼容的版本中选择，不因最新版本较新就强推，安装仍由用户触发。

**兼容性验收矩阵**

| 输入或操作 | 必须观察到的结果 |
| --- | --- |
| 同一格式目录含兼容主题 A、未知未来类型 B、兼容 Skill C | A/C 正常显示、筛选和安装；B 显示安全摘要及不支持原因，不能安装；整个目录不报废 |
| 已知类型使用未知 role 或新 contract | 对应版本不兼容，main 安装入口也拒绝；不回退到旧 contract 或默认 owner |
| 一个包同时含兼容 TTS 和未知贡献 | 整包禁止安装/更新，无部分配置提交、Runner 启动或贡献注册 |
| 某包 v1 已安装，v2 兼容，v3 引入未知类型 | 保留 v1 正常运行；v3 不作为更新推荐，仍允许查看并推荐合格的 v2；用户不能绕过 main 安装 v3 |
| 同格式增加规范允许的可忽略展示字段 | 旧端保留原有操作语义，忽略该字段；不把它解释成权限或新能力 |
| 兼容信息缺失、必需语义未知，或未来依赖交付格式不可理解 | 对应版本不能安装，显示原因；不能因为“已审核”而放行或偷偷走本地依赖下载 |
| 未知类型 B 与已安装兼容包 A 的安全封禁同时发布 | B 不兼容，但 A 的封禁和发布序号正常持久提交并生效；跳过 B 不能遗漏安全更新 |
| 未知目录格式主版本、身份冲突或损坏安全结构 | 整份新快照拒绝，序号不推进、不覆写旧安全事实；显示需升级客户端或刷新失败，不声称已检查最新安全状态 |
| 下载的 wheel 与目录摘要/贡献要求不符 | 既有完整检查拒绝，不因目录列表已经展示过而减少验证 |
| 应用降级后，已经安装的包包含旧 Host 不支持的贡献 | 保留可验证的身份、数据和管理/移除路径，拒绝执行；不伪造已加载、不自动卸载或部分激活 |

首版使用固定 reader 加合成未来目录，并断言被拒条目没有 pip、Runner、主题准入或持久安装提交；这不要求实现未来能力。下一次实际扩大类型或目录交付格式时，用上一受支持客户端和新目录重复此矩阵，连同新端正常使用测试保存精确版本证据。

**阶段与落点**

| 阶段 | 本节对应工作 | 主要验收 |
| --- | --- | --- |
| D0/D1 | 作者文档明确三层结论，通用检查保持独立 | 通用 Host 接受与目录拒绝可同时成立，原因可定位 |
| S0 | 目录 schema 的字段兼容规则、审核政策集中、未来 fixture | 新 kind/contract 不破坏稳定目录格式，安全结构仍严格 |
| S1 | `extensionCatalog.ts` 逐条判断，main/installer 最终准入 | 整包拒绝、无部分副作用、安全更新不被条目过滤丢掉 |
| S2 | 不兼容卡片、版本选择和升级提示 | 兼容条目继续可用，已安装旧版本不受不兼容新版本影响 |
| S3 | 固定 reader/旧客户端与新目录交叉验收 | 保存矩阵结果，不将仅新端通过当作旧端兼容 |
| 后续新类型立项 | 最小契约、原生 owner、示例、profile 和专属审核项 | 正反运行与混合包生命周期通过后才开放生产类型 |


## 2026-10-23：投稿流程补充与减负

作者路径固定为“一次预检、一个 PR”。首次附可核查的归属和权利依据，更新复用已有依据并补变更/迁移说明；不要求作者重填产物可推导元数据、虚构审核人、组织审核班子或另开发布 PR。已有 README、发布说明和测试日志均可复用。返修在原 PR，实质修改只重做受影响的检查。维护者承担最终目录记录、评审交接、可批量的发布 PR 和上线验收，标签可选，不增加账号后台或状态数据库。
