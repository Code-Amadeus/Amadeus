## 2. 本轮已经交付什么

- SDK `0.1.0` wheel 摘要为 `274bd66b81932c8ea50f39f58e7bf91530a8015196acfcf9bcfd77fa2d8b8084`；Node 校验固定清单，安装器不再写死文件名。
- 默认 `npm run build` 不需要 Python/setuptools 来构建 SDK。桌面安装从随 Host 交付的 wheel 准备环境，不从外部下载或构建 SDK。
- 安装前检查插件声明的 SDK 范围、精确版本与直接来源要求；不兼容时在 pip 之前给出原因。传递依赖冲突仍由 pip resolver 处理。
- SDK 带 PEP 639 许可元数据和 LICENSE。规范构建统一文本换行、ZIP 属性及 RECORD，锁定开发依赖；Windows/Linux CI 独立构建并比较实际字节。
- 安装/更新披露包含作者声明的许可证、完整 wheel 摘要、本地来源文件、贡献、命令及 OS 声明。
- 主题 token 白名单、清单校验器、示例和共享颜色用例已有固定来源与漂移检查；真实 Host 的字体、图像解码和对比度仍是运行环境责任。

这是 L1 与收窄 K1 的交付。公开 PyPI 发布不属于本轮，也不是现有 Host 安装、记忆设计或后续校验工具的前置条件。
已有协议/Host 回归和真实进程验收；不能再写“没有一致性测试”。尚未交付的是面向作者的统一工具体验。

## 3. 后续作者工具候选

| 候选 | 尚需完成的工作 | 验收 |
|---|---|---|
| K2 共享包规则与 validate | 在现有 manifest 固定副本之上，厘清 wheel/配置/资源检查归属；提供统一作者校验入口 | 同一组有效/无效包在 CLI 与 Host 安装路径得到一致结论和可定位原因，不把字体/原生解码伪装成静态保证 |
| K4 离线合约检查 | 面向 TTS/MCP/Skill 的可运行检查，复用已实现契约 | 有效示例真实发现/调用；错误握手、取消、清单不一致和无效资源按各自边界失败 |
| K5 模板与首批作者 | 以已开放的 TTS/MCP/Skill/主题为模板，文档可在干净环境复现 | 外部作者实际完成安装、使用、更新与卸载；反馈进入独立问题记录，不以复制文件为成功 |
| K3 开发模式与诊断日志 | 按真实作者反馈单独设计原地目录引用、重新加载和受控诊断输出 | 保持同一安装/配置 owner、同一生效边界；日志有明确开关、脱敏和保留策略 |

推荐先厘清 K2，并以最小 K4/K5 验证作者是否能独立完成一个插件，再决定 K3 的投入。
这是候选优先级，不是开工授权；不因阶段编号要求串行完成全部项目。
更广类型、商店、签名强制、自动更新、通用热重载和回滚继续另行评审。

## 4. 不可改变的边界

- 安装不等于启用或授权；Main Chat 不直接运行 MCP/Skill/插件。
- 作者工具校验包，不授予 Host 能力，也不根据 README/脚本自动扩大权限。
- 开发目录将来即使开放，也复用相同身份、记录、绑定和原生生效边界；不能偷偷引入后端热切换。
- 非密钥配置与密钥保持现有来源规则；第三方日志不得包含 Host 的全量环境、明文绑定或用户历史。
- SDK 版本来自单一固定清单，Host 不隐式追踪协议仓 main；每次更新仍需 pin、许可和验收。
- 规范与实现只承诺已验证的子集。进程隔离不是 OS 沙箱，跨平台构建不等于完整 GUI 资格。
